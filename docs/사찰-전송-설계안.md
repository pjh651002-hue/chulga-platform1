# 사찰 전송 기능 설계안

> 작성 기준일: 2026년 9월 26일 · 대상: 출가 플랫폼 시제품
> 이 문서는 **코드를 쓰기 전에 종단이 정해야 할 것**을 정리한 것입니다.
> 기술 설계보다 운영 결정이 먼저입니다.

---

## ⛔ 상태: 보류 (2026.09.26)

**사찰이 신청을 받으려면 당해 사찰과 협의 절차가 선행되어야 하므로,
이 기능은 앱에서 빼기로 했습니다.**

- 동작하지 않던 「고른 곳에 보내기」 버튼, 조회 코드 발급, 진행 단계 표시를
  코드에서 제거했습니다.
- 지금은 추천 사찰마다 **홈페이지·종무소 전화·모집문의 번호**를 바로 걸어 주고,
  어디에 물을지 모르는 분께는 출가상담전화를 안내합니다.
- 앱은 이제 **어디에도 아무것도 보내지 않습니다.** 입력한 조건은 기기 밖으로
  나가지 않습니다.

아래 설계는 **사찰 협의가 이루어진 뒤 다시 꺼내 보시라고** 남겨 둡니다.
특히 4장(회신 채널)과 7장(종단이 정해야 할 것)이 협의 자리에서 바로 쓰입니다.
5장의 기술 결함 세 가지는 그때 반드시 함께 고쳐야 합니다.

---

## 1. 무엇이 끊겨 있나

지금 이용자는 조건을 넣고, 안내를 받고, 사찰을 고르고, **「고른 곳에 보내기」를
누릅니다.** 그리고 아무 일도 일어나지 않습니다.

```js
// index.html · 현재 코드
if(sb)sb.onclick=()=>{
  const cs="ABCDEFGHJKLMNPQRSTUVWXYZ23456789";let r="";
  for(let i=0;i<5;i++)r+=cs[Math.floor(Math.random()*cs.length)];
  state.code="출가-"+r; renderMatch();     // 코드만 만들고 끝납니다
};
```

화면은 "보냈습니다"라고 말하고 조회 코드를 줍니다. **전송도 저장도 하지
않습니다.** 푸터에 "실제로 동작하지 않습니다"라고 적혀 있지만, 그 문구를 읽고
누르는 사람은 드뭅니다.

**출가자 증대의 관점에서 이것이 가장 큰 손실입니다.** 조건을 다 입력하고 사찰까지
고른 사람은 이 앱에서 가장 멀리 온 사람입니다. 그 지점에서 끊깁니다.

---

## 2. 핵심 긴장 — 익명성과 회신 가능성은 함께 갈 수 없습니다

현재 화면은 이렇게 약속합니다.

> "고르신 곳에만 조건이 전달되며, **이름과 연락처는 보내지 않습니다.**"
> "이후 연락은 발급받으신 코드로 이 앱 안에서만 이루어집니다."

익명성을 지키려는 좋은 설계입니다. **그런데 이 약속에는 대가가 있습니다.**

사찰이 답을 써도, 이용자가 **스스로 앱에 다시 들어와 코드를 넣어야** 그 답을
봅니다. 코드를 적어두지 않으면 영영 못 봅니다. 화면도 그걸 인정합니다.

> "이름을 남기지 않으셨으므로 코드를 잃으면 조회가 어렵습니다."

**(추정)** 출가 결심은 대개 긴 숙고를 거치는데, 며칠 뒤 코드를 들고 돌아오는
비율은 높지 않을 것으로 봅니다. 이건 검증이 필요한 가설이며, **3번에서 붙인
퍼널 수집이 바로 이 숫자를 재기 위한 것**입니다.

**이 긴장을 어떻게 풀지가 이 기능의 핵심 결정입니다.** 아래 4장에서 선택지를
정리했습니다.

## 3. 전달 경로 — 어떻게 사찰에 닿게 할 것인가

| | A. 사찰에 직접 이메일 | B. 종단 중계 (권고) | C. 사찰별 계정 대시보드 |
|---|---|---|---|
| 방식 | 종무소 메일로 자동 발송 | 교육부 화면에 모이고, 담당자가 사찰에 전달 | 사찰마다 로그인해 확인 |
| 사찰 준비 | 메일 주소만 | 없음 | 계정 발급·교육·유지 |
| 응답 관리 | 불가 (보내고 끝) | **가능 — 미응답 추적** | 가능 |
| 통합 통계 | 어려움 | **쉬움** | 중간 |
| 착수 속도 | 빠름 | 빠름 | 느림 |
| 위험 | 메일 누락·스팸함 | 교육부 업무 부담 | 사찰별 역량 편차 |

### 권고: B (종단 중계)부터

세 가지 이유입니다.

1. **정책 방향과 일치합니다.** 종단이 2026년 밝힌 방향은 "체험자 통합관리와
   멘토링·상담 연계체계 마련"입니다(불교IN 보도). B가 그 체계의 실무 도구입니다.
2. **사찰에 아무 준비도 요구하지 않습니다.** A와 C는 전국 사찰의 준비 상태에
   좌우되지만, B는 교육부 한 곳만 준비되면 시작됩니다.
3. **미응답을 볼 수 있습니다.** 어느 사찰이 며칠째 답이 없는지 보이지 않으면
   전송 기능은 있어도 없는 것입니다.

C는 신청이 쌓이고 사찰별 처리량이 확인된 뒤 2단계로 넘어가는 것이 맞습니다.

## 4. 회신 채널 — 이용자에게 어떻게 답이 닿게 할 것인가

**이것이 가장 중요한 결정입니다.** 아래 셋 중 하나를 골라야 합니다.

| | ① 코드 조회 (현 설계) | ② 이메일 선택 입력 | ③ 휴대전화 선택 입력 |
|---|---|---|---|
| 개인정보 | **수집 없음** | 이메일 수집 | 전화번호 수집 |
| 법적 부담 | 거의 없음 | 동의·보관·파기 절차 필요 | ②와 같음 + 본인확인 쟁점 |
| 회신 도달 | **낮음 (추정)** | 중간 | 높음 |
| 재방문 필요 | 필요 | 불필요 | 불필요 |
| 만 14세 미만 | 문제 없음 | 법정대리인 동의 문제 발생 | 같음 |

### 권고: ①을 유지하되 ②를 **선택 항목**으로 추가

- 기본은 익명(①)으로 두고, **"답이 오면 알려드릴까요?"**라고 물어
  이메일을 **원하는 사람만** 적게 합니다.
- 적지 않아도 신청은 그대로 접수됩니다. 적은 사람에게만 알림을 보냅니다.
- 이렇게 하면 익명을 원하는 사람의 선택을 지키면서, 회신 도달률을 올릴 수 있습니다.

③(휴대전화)은 도달률이 가장 높지만 **출가라는 사안의 민감성**을 생각하면
권하지 않습니다. 가족에게 알리지 않고 알아보는 사람이 적지 않을 것으로 보이며
**(추정)**, 문자가 오는 것 자체가 부담이 될 수 있습니다.

> **만 14세 미만 쟁점**: 이메일을 받기 시작하면 개인정보 수집이 시작되고,
> 앱이 만 13세부터 안내하므로 법정대리인 동의 문제가 실제로 발생합니다.
> `docs/개인정보처리방침-초안.md` 2-(1)을 함께 보십시오.

## 5. 지금 코드에서 반드시 고쳐야 할 것

설계와 별개로, **현재 코드에는 그대로 두면 안 되는 결함이 셋 있습니다.**

### (1) 조회 코드를 브라우저에서 만듭니다

`Math.random()`으로 만듭니다. 암호학적 난수가 아니어서 **예측 가능**하고,
서버가 모르는 값이라 중복도 막지 못합니다.

**→ 서버에서 암호학적 난수로 발급해야 합니다.**

### (2) 코드만으로 조회됩니다 — 무작위 대입에 뚫립니다

현재 형식은 32종 문자 5자리로 **약 3,355만 가지**입니다. 많아 보이지만,
속도 제한이 없으면 자동화 도구로 남의 신청 내용을 긁을 수 있습니다.
신청 내용에는 성별·나이·지역이 들어 있습니다.

**→ 세 가지를 함께 적용해야 합니다.**
- 코드 길이를 8자 이상으로
- 조회 API에 속도 제한 (IP·코드 단위)
- 신청 시 이용자가 정한 **네 자리 확인번호**를 코드와 함께 요구

### (3) 코드를 잃으면 복구 경로가 없습니다

화면도 인정하고 있습니다. ②(이메일 선택 입력)를 도입하면 **적은 사람에 한해**
재발급 경로가 생깁니다.

```

  │ 조건 입력                      │                      │
  │ 사찰 선택                      │                      │
  │ ──── POST /api/apply ────────▶ │                      │
  │      성별·연령대·지역·기간     │                      │
  │      선택 사찰, (선택)이메일   │                      │
  │ ◀──── 코드 + 확인번호 ─────────│                      │
  │                                │ ─── 전달·독려 ─────▶ │
```

### 저장 항목

3번에서 만든 퍼널 테이블과 **분리**해야 합니다. 퍼널은 익명 집계, 이건 개별 건입니다.

| 항목 | 비고 |
|---|---|
| 코드 | 서버 발급, 8자 이상 |
| 확인번호 해시 | 평문 저장 금지 |
| 성별, 연령대, 지역, 희망 기간 | **정확한 나이는 저장하지 않음** |
| 선택 사찰 목록 | |
| 이메일 (선택) | 적은 사람만. 암호화 저장 |
| 상태 | 접수 / 전달 / 응답 / 종결 |
| 사찰 응답 본문 | |
| 접수일, 파기예정일 | |

### 보관기간

**제안: 응답 뒤 90일, 미응답이면 접수 뒤 180일.** 이후 자동 파기.
이메일은 종결 즉시 삭제하고 나머지는 익명 통계로만 남기는 방식도 가능합니다.

## 7. 종단이 결정해야 할 것

**코드는 여기서 더 나갈 수 없습니다.** 아래가 정해져야 착수합니다.

| # | 결정 사항 | 정해야 할 곳 | 권고 |
|---|---|---|---|
| 1 | 전달 경로 | 교육부 | B (종단 중계) |
| 2 | 회신 채널 | 교육부 + 법무 | ① + ② 선택 입력 |
| 3 | 교육부 내 담당 부서·담당자 | 총무원 | — |
| 4 | 사찰 응답 목표 기한 | 교육부 | 예: 영업일 3일 |
| 5 | 미응답 시 처리 | 교육부 | 담당자 독려 후 타 사찰 안내 |
| 6 | 보관기간·파기 절차 | 법무 | 위 6장 제안 |
| 7 | 만 14세 미만 이용자 취급 | 법무 | 처리방침 초안 2-(1) |
| 8 | 개인정보처리방침 게시 | 법무 | 착수 전 필수 |
| 9 | 운영자 화면 인증 방식 | 교육부 | 현재 공개 링크 |

**1·2번만 정해 주시면 나머지는 기본값으로 두고 구현을 시작할 수 있습니다.**

## 8. 단계별 도입

| 단계 | 내용 | 선행 조건 | 상태 |
|---|---|---|---|
| 0 | 전송 문구를 걷어내고 사찰 직접 연락으로 안내 | 없음 | **완료 (2026.09.26)** |
| 1 | 신청 접수 + 교육부 화면 + 코드 조회 | **사찰 협의** + 결정 1·3·6·8 | 보류 |
| 2 | 이메일 선택 입력 + 알림 | 결정 2·7 | 보류 |
| 3 | 사찰별 계정 대시보드 | 1단계 운영 실적 | 보류 |

0단계를 마쳤으므로, 지금 이 앱에서 출가로 이어지는 경로는 **사찰 홈페이지 클릭과
전화 걸기** 둘뿐입니다. 3번에서 계측한 `apply_click`과 `tel_click`이 바로 그
경로를 재는 지표이며, **1단계 착수 여부를 판단할 근거가 됩니다.** 이 숫자가
충분히 쌓이면 협의 자리에서 "이만큼이 실제로 사찰 문을 두드렸다"고 말할 수 있습니다.

## 9. 위험

| 위험 | 대응 |
|---|---|
| 신청은 쌓이는데 사찰이 답하지 않음 | 미응답 추적 화면. 4·5번 결정 필요 |
| 코드 조회 무작위 대입 | 5-(2) 세 가지 조치 |
| 이메일 유출 | 암호화 저장, 종결 시 즉시 삭제 |
| 장난 신청 | 속도 제한. 개인정보가 없어 피해는 제한적 |
| 교육부 업무 과부하 | 1단계 운영량을 보고 3단계 판단 |
